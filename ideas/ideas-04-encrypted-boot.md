# Idea 4: Bring encrypted boot instructions and installer into agreement

This note expands idea 4 from [ideas.md](./ideas.md). The purpose is to make
the boot chain and recovery guide describe the same encrypted-root layout.

## What the repository does today

The README's install TODO records a move to `sd-encrypt`, a changed hook list,
and UUID-based `rd.luks.name` parameters. `base_include` still edits the
`encrypt` hook and writes a `cryptdevice=LABEL=linux:luks` option. The notes
therefore document a boot configuration different from the one generated by
the installer.

Arch's initramfs and systemd-boot instructions change over time. Do not copy a
kernel parameter from a recovery note without checking it against the current
installed `mkinitcpio` hooks and the actual boot entry format.

## Recommendation

Choose one currently supported initramfs design, derive the encrypted-device
UUID from the partition created by the script, and generate matching hook and
boot-entry settings from that value. Keep the generated result inspectable
before reboot. Update recovery instructions from a successfully tested live
USB procedure rather than from memory.

## Proposed changes

1. Confirm the chosen `mkinitcpio` preset and whether the system uses the
   systemd-based or busybox-based initramfs hooks.
2. Query the LUKS UUID from the validated crypt partition and put it into the
   corresponding boot parameter; do not assume the device label is unique.
3. Make hook updates idempotent and verify the resulting hooks before running
   `mkinitcpio`.
4. Generate the loader entry from variables and print it for review before
   rebooting.
5. Rewrite README installation and rescue instructions to match the tested
   layout, including partition discovery, unlock, mount, chroot, initramfs
   rebuild, and bootloader recovery.
6. Validate a fresh install and recovery boot in a VM using the current Arch
   ISO; test both expected success and a deliberately incorrect UUID.
